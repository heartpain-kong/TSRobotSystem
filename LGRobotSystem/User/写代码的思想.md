# 写代码的思想

> 这份文档讲的是**为什么这么写**。规则可以背，思想只能理解 —— 理解了，遇到新情况你自己就能判断。
> 配套：`代码架构框架.md`（结构）、`代码风格与模板.md`（写法）、`每次cubemx导出必做事情.md`（流程）。

---

## 1. 代码首先是**给下一个人看的**，其次才是给机器跑的

机器只关心对不对。但真正的时间成本在**改**：三个月后的你、新来的队友、临时被叫来救火的人。
所以本工程的选择是：

* **可诊断 > 简洁**：宁可多一个 `Rx_Frames / Crc_Errors / Lost_Count`，也不要出问题时靠猜 ✓
* **显式 > 聪明**：不用模板元编程、不用运算符重载、不用"炫技"的写法 ✓
* **一层一件事**：一个文件里既有外设初始化又有控制逻辑的代码，一定会在半年后变成没人敢改的东西 ✓

> 判断标准：**"我不在的时候，别人能不能只靠 md + 代码就把这个模块改对？"**

---

## 2. 分层：依赖只能**单向下**，通用性只能**往上增**

```
App(业务,最易变)  →  Device(设备)  →  Bsp(板级)  →  HAL/CubeMX
        ↘_______________ algorithm(纯算法,谁都能用,它谁都不依赖) _______________↙
```
* 越往下越**通用**、越**稳定**、越**不该知道业务** ✓
* `algorithm` 里出现 `HAL_*` ✗、`Bsp` 里出现"底盘" ✗、`Device` 里出现"模式" ✗ —— 这三个都是**层次泄漏** ✓
* 好处很实际：换机器人只改最上面一层 ✓；算法能被单独测 ✓；Bsp 能在另一个工程复用 ✓

---

## 3. **单一数据源 / 单一主人**

* 一个外设（一颗 Flash、一个串口）只有一个"主人" ✓
  （例：`bsp_flash` 与 `Log_Task()` 共用 W25Q64 状态机 ⇒ 必须同一个任务调用 ✓）
* 一个话题只有一个**生产者** ✓（多个消费者没问题 ✓）
* 一个"该配在哪"只有一个地方 ✓（电机分配、几何参数、机构类型全在 `robot_def.h` ✓）
* 一个换算只有一处 ✓（电机 rpm ↔ rad/s 只在 `motor_task` ✓）

> 反例（真踩过）：底盘和云台各写各的电机下标 ⇒ 装车时两个任务抢同一路电机，现象是"电机乱动"，查一下午 ✗

---

## 4. 任务之间：**用数据流，不要互相调用**

任务 A 直接调任务 B 的函数、或读 B 的全局变量，会立刻带来三个问题：
谁先跑？谁阻塞谁？改 B 会不会挂 A？ ✗

所以本工程任务间只有两种关系：
* **生产/消费**：`Msg_Publish` →（环形数组）→ `Msg_Latest` ✓ 生产者**不知道**消费者是谁 ✓
* **服务**：`Init()` 时拿到接口，运行时不互相调用 ✓

> 环形数组的语义也要挑对 ✓：**控制类看"最新"**（`Msg_Latest` ✓ 旧的丢掉无所谓 ✓）；
> **记录类才用"队列"**（`Msg_Pop` ✓ 一条都不能少 ✓）。

---

## 5. 控制回路：**晚绑定、早安全**

* **晚绑定**：谁给目标（遥控器 / 视觉 / 自动）在**运行时**决定 ✓，控制回路本身不关心来源 ✓
  （`cmd` 把三路输入揉成一份 `Cmd_Data_t`，后面的任务只见指令、不见来源 ✓）
* **早安全**：任何异常都要**立刻回到安全态**，而且安全态要**显式定义** ✓
  * 遥控器掉线 ⇒ `CMD_MODE_IDLE`：**全零**（不是"保持上一次" ✗）
  * 舵轮指令为 0 ⇒ **保持上次转向角**（不是回零 ✗ 回零会甩轮 ✓）
  * 云台不使能 ⇒ **锁在当前角**（不是零力矩 ✗ 会自由倒下 ✓）
  * 发弹门控 ⇒ "指令使能 && 裁判允许 && 热量有余量"三者**与** ✓

### ★ 失效方向的取舍（这一条最容易被忽略）
| 情况 | 该 fail 到哪边 | 例子 |
|---|---|---|
| **执行器的目标** | **fail-safe**（停下/归零）| 遥控掉线 ⇒ 底盘指令全零 ✓ |
| **权限/门控** | **fail-open**（放行）| 裁判系统没接 ⇒ 不拦（否则练习时打不了 ✓）；决策层没数据 ⇒ 先允许动 ✓ |
> 一句话：**"该动的东西"没数据就停 ✓；"该拦的东西"没数据就放 ✓** —— 反了会出人命或出不了活 ✓

---

## 6. 实时性：**每个任务有预算，超了要看得见**

* 1 kHz 任务里只放 **µs 级**的事：算乘法、写寄存器、`memcpy` 数据 ✓
* **阻塞的事丢给低频任务**：Flash 写一页 0.4 ms ✗ ⇒ 绝不在控制回路里写 ✓（日志只进内存环形 ✓，落盘交给 100 Hz 的 `Log_Task` ✓）
* 每个任务都有**超时计数**（`xxx_task_overrun` ✓）—— 它一直涨，说明这拍根本算不完 ✓ 这是最便宜的"性能监控" ✓
* **中断只搬运**：ISR 里只 `memcpy` + 置标志 ✓；组帧、CRC、`Msg_Publish` 全部放任务 ✓
* **临界区只护"下标 + 一次拷贝"**（`__disable_irq()` 几 µs ✓），不要在临界区里算浮点/打印 ✗

---

## 7. 内存：**静态、定长、编译期能查出问题**

* **不用 `malloc` / `new`** ✗（嵌入式跑久了必碎 ✓）
* 环形数组、任务栈、缓冲全是定长静态 ✓
* 每条消息的**长度上限编译期就断言** ✓：
  ```cpp
  static_assert(sizeof(Xxx_Data_t) <= MSG_SLOT_SIZE, "超过 MSG_SLOT_SIZE 会被静默拒收");
  ```
  > 这条救过命：IMU 帧 92 B > 当时的上限 64 B ⇒ 会被**静默拒收**（现象是"话题就是没数据" ✗ 极难查 ✓）。
  > **能编译期发现的错，绝不要留到运行时** ✓ —— 这是本工程的一条硬规矩 ✓

---

## 8. 契约：单位和协议要**写进文档**，而且只有一处换算

* 对外一律 **SI**：角度 rad、角速度 rad/s、长度 m、速度 m/s、力矩 N·m ✓
* 电机接口一律**关节侧**（各品牌内部的减速比/刻度换算在类里做 ✓）
* 底盘算法输出 **rpm**（历史与参考工程一致 ✓）⇒ 换算**只在 `motor_task_*_wheel_rpm()` 一处** ✓
* 协议（帧格式、CRC 范围、`data_length` 从哪算起）**必须写进 md** ✓ —— 因为这种错"看起来能跑，就是偶尔丢一帧"，不写文档下次还会踩 ✓

---

## 9. 可诊断性：**出问题时，第一眼要能看到卡在哪**

本工程在这上面花了不少心思，都是值得的 ✓：
1. **错误码量化**（`error_task`）：区分到"第几台电机初始化失败/离线/报错" ✓
2. **声光同时编码**：蜂鸣器声数 + 8 颗灯的二进制（LED0 = 类别色）✓ —— 现场不用接串口就知道码 ✓
3. **每个设备都有统计量**：收到几帧、CRC 错几次、丢了几次 ✓ —— 一眼区分"线的问题"还是"我协议实现的问题" ✓
4. **关键数据 10 Hz 落盘**（外部 Flash ✓ 掉电也在 ✓）：当时的指令、实际姿态、状态 ✓
5. **调试变量**：`volatile` 全局量，调试器直接看 ✓（`g_fault_code` / `g_thread_create_failed` / `*_init_ok` / `*_overrun` ✓）
6. **不吞错误**：`osThreadNew` 返回值必查 ✓；外设 `HAL_xxx_Init` 的结果要存进 `*_init_ok` ✓

> 反面教材：`HAL_Init()` 失败直接 `while(1);` ✗ —— 现场什么都看不到。
> 正确做法：**记下来 + 报出来**（`g_fault_code` + 红灯 ✓），让设备"带着故障继续说话" ✓

---

## 10. 移植别人的代码：**保结构、记出处、别自作聪明**

* **保留原算法结构、参数含义、变量名含义** ✓（只改命名/格式 ✓）
  —— 官方调好的参数（EKF 的 Q/R/λ、PID 的量纲）不要"顺手优化" ✗
* **"看着奇怪但故意"的地方原位保留 + 注释说明** ✓
  （例：四元数 EKF 里 `temp_vector.pData[3] = 0.0f` 是"不修正 yaw 轴"，官方与参考工程都这样 ✓）
* md 里写清：**移植自哪个工程/哪个文件、我改了什么、哪些参数是官方调好的** ✓
* 参考工程里**明知有问题的做法**（例：`message_center` 用链表 + `malloc` ✗）要**看懂它的意图再重写** ✓，
  不要照抄 ✗，也不要因为"它那么写"就放弃更好的做法 ✓

---

## 11. 渐进式验证：**不带病前进**

每加/改一个模块，固定三步 ✓：
```
① 编译过(exit 0,无警告)
② tools\cubemx_post_export.ps1 自检全绿
③ 按自己 .md 的「上板自检」过一遍(不接设备时/正常时/注入异常时 都测)
```
> 为什么要写"上板自检"这一节？因为**编译过 ≠ 能工作** ✓。
> 一份没写上板自检的 md，等于没写 ✓（新人也不知道该测什么 ✓）

---

## 12. 配置集中：**换机器人只改一处**

* `robot_def.h`：任务周期/优先级/栈 + **电机分配** + **几何参数** + **机构类型** ✓
* 一个宏控制一个差异 ✓（例：`HIGHRISE_MECH_SHOOT / LIFT` —— RC(ROBOCON) 与 RM 共用系统的差异就这一个宏 ✓）
* 好处：**看一个文件就知道这台车是什么车** ✓；改配置不会漏改 ✓

---

## 13. 文档与代码同寿

* 每个模块 **`.h / .cpp / .md` 三件套** ✓，说明写在 md 里 ✓，代码里只留"为什么" ✓
* md 必须包含：定位（在数据流哪一环）、每拍做什么、API、**要按实车改的参数**、**坑**、**上板自检** ✓
* 变动代码时**顺手改 md** ✓ —— 一份过期的文档比没有文档更害人 ✓

---

## 14. 我们**不做**的事（同样是设计决定）

| 不做 | 为什么 |
|---|---|
| 动态内存 | 碎片、不可预测、出了问题最难查 ✗ |
| 模板元编程 / 复杂泛型 | 编译慢、报错难懂、队友看不懂 ✗ |
| RTOS 高级特性（事件组/流缓冲/消息队列）滥用 | 环形数组 + 简单任务已经够；多一种机制就多一处能出错的地方 ✓ |
| 为了"少写几行"把两层混在一起 | 省下的时间会在第一次改动时连本带利还回去 ✗ |
| 在中断里做重活 | 抖动、优先级反转、玄学卡死 ✗ |
| 静默失败（不检查返回值 / 不报错） | 现场最贵的不是"报错"，是"什么都没发生" ✗ |

---

## 15. 最后：写代码的四个提问（遇到犹豫时问自己）

1. **它属于哪一层？** —— 放错层，后面全歪 ✓
2. **谁是它的唯一主人 / 唯一数据源？** —— 有两个，就会打架 ✓
3. **出错了会怎么表现？我怎么一眼看出来？** —— 想不出来就先加统计量 ✓
4. **下一个人要改它，需要知道什么？** —— 那就写进 md ✓
